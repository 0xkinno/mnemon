# Virtuals ACP v2 Setup

MNEMON can use ACP only for a genuinely unresolved `CONTESTED` decision. The current ACP v2 SDK requires:

1. A buyer/evaluator agent registered at `https://app.virtuals.io/acp/new`.
2. A provider agent with an offering that accepts the evaluation requirement.
3. A Privy `walletId` and signer private key for each agent. The signer must be the Privy wallet-authorization signer generated by the ACP agent Signers flow (PKCS#8 PEM or equivalent supported signing function), not an ordinary 32-byte EVM wallet key.
4. Distinct buyer and provider wallet addresses.
5. Base wallet funding for job creation and, if applicable, USDC funding for the job budget.
6. The provider offering name and requirement schema.

The current SDK is documented in `research/acp-node-v2/README.md` at the pinned repository checkout. The execution sequence is:

```text
MNEMON CONTESTED
  -> ACP buyer creates job by provider offering
  -> provider submits evaluation deliverable
  -> buyer/evaluator completes the job
  -> result is written to Sibyl COLD
  -> MNEMON recomputes the verdict
  -> Base anchors the resolved receipt
```

Required local variables are listed in `.env.example`. Never place ACP signer keys in frontend code or commit `.env.local`.

No ACP transaction is claimed until `proof/acp_arbitration.json` contains a real job id, participants, timestamps, deliverable, and independently inspectable settlement evidence.

## Tooling

| Path | Role |
| --- | --- |
| `scripts/acp_arbitrate.ts` | Buyer/evaluator runner. Creates (or attaches to) one job, funds it, resolves and validates the deliverable, completes the job, and writes the proof only after the on-chain status reads back `COMPLETED`. |
| `scripts/acp_inspect.ts` | Independent verification. Rebuilds a job's full on-chain event history and status, and with `--bind-deliverable <path>` proves the submitted hash equals keccak256 of the posted body. |
| `scripts/acp_preflight.mjs` | Deliverable validator. Enforces that the body parses as JSON and carries the five required string fields, and prints sha256/keccak256. |
| `scripts/acp_provider_submit.mjs` | Provider submit path. Runs the pre-flight check, then invokes the ACP CLI through a direct argv so the posted body and the hashed body are byte-identical. |
| `experiments/acp_requirement.py` | Builds the real `CONTESTED` state in `.acp-memory.db` and emits `proof/acp_requirement.json`. |
| `experiments/acp_deliverable.py` | Produces the provider's adjudication deliverable from the requirement. |
| `experiments/acp_persist_result.py` | Persists the ACP verdict into Sibyl COLD (`persist`) and re-reads it in a fresh process (`read`). |

Typical run, in order:

```text
experiments/acp_requirement.py                      # real CONTESTED state
npx tsx scripts/acp_arbitrate.ts                    # buyer creates the job, prints jobId
acp provider set-budget --job-id <id> --amount 0.01 --chain-id 8453 --json
node scripts/acp_provider_submit.mjs --job-id <id>  # pre-flight + submit
npx tsx scripts/acp_inspect.ts <id> --bind-deliverable proof/acp_deliverable.json --out proof/acp_job_<id>.json
experiments/acp_persist_result.py                   # -> Sibyl COLD
experiments/acp_persist_result.py read              # fresh-process reconstruction
```

## Deliverable contract

The evaluator accepts a deliverable only when it parses as JSON and every one of `decision`, `winning_claim`, `reason_code`, `evidence_digest`, and `adjudicated_at` is a non-empty string. `scripts/acp_preflight.mjs` enforces the same rule before submission, and `scripts/acp_provider_submit.mjs` refuses to submit a body that fails it.

Provider adjudication policy for `independent_memory_adjudication`, implemented deterministically in `experiments/acp_deliverable.py`:

- a `risk_verdict` is a safety signal, so when two witnesses in the same epoch assert conflicting verdicts and neither claim hash is corrupted, the more conservative claim is upheld;
- `decision` is `UPHELD`, `winning_claim` is the upheld status, `evidence_digest` is that claim's hash, and `reason_code` is `safety-dominant-witness-upheld`.

## Operational rules

These are not style preferences; each one is the fix for an observed failure on Base Mainnet.

1. **One runner per agent.** Two `scripts/acp_arbitrate.ts` processes subscribed to the same buyer agent will both act on `job.submitted`, and a reject can beat a complete. Pin a runner with `--job <id>` and let it exit; it has a hard `--timeout-minutes` so it can never linger.
2. **Never reject an unreadable body.** An empty deliverable read is an indexing or SSE race, not a malformed deliverable. The runner reports `deliverable-missing` and exits; it only rejects on genuinely invalid JSON or a missing required field.
3. **Verify settlement before claiming it.** The SDK's `waitForCallsStatus()` resolves as soon as a receipt exists and does not inspect the receipt status, so a reverted `complete()` still looks successful. `scripts/acp_arbitrate.ts` re-reads the job status on-chain and writes `proof/acp_arbitration.json` only on `COMPLETED`; otherwise it writes `proof/acp_arbitration_failure.json`.
4. **Hash the exact bytes you post.** `acp provider submit --deliverable "<json>"` is unusable from PowerShell 5.1, which mangles embedded quotes and makes the on-chain hash disagree with the posted body. Use `scripts/acp_provider_submit.mjs`, which passes the raw JSON through a direct argv.

## Current state

Job `78185` completed the full lifecycle on Base Mainnet for a real `CONTESTED` claim, with settlement verified on chain and the verdict persisted into Sibyl COLD. Two earlier jobs were terminal: `77935` expired before delivery, and `77954` was rejected and refunded because its deliverable body was never retrievable by the evaluator, so the hash arrived without the content (`proof/acp_job_77954.json`). A third, `78154`, posted a 247-byte body whose on-chain hash matched, but was rejected by a stale pre-fix runner that was still subscribed to the buyer agent (see `proof/acp_arbitration_failure.json`). `77954` is terminal and cannot be revived; a fresh job is always required.

The ACP outcome is anchored on Base Sepolia by transaction `0xf6c2ee4127309c46512ea6d52ad85daec06f02c6214f77f919c138a5fd8b5269` (block `46637732`), whose decoded event carries the same claim hash, epoch, and operation id as the Sibyl COLD witness. `proof/final_e2e_chain.json` re-derives that binding and reports `linkage_verified: true`; `proof/base_acp_resolution.json` is the anchor artifact. `experiments/final_base_link.py` performs only the minimum commitment needed to establish this linkage — it does not create another ACP job.

The provider path is what makes a fresh job succeed. `scripts/acp_preflight.mjs` rejects a body that does not parse as JSON or that is missing any of the five required string fields, and `scripts/acp_provider_submit.mjs` submits the exact bytes it validated, so the posted body and the hashed body are byte-identical. Do not post deliverables through PowerShell string interpolation.

No ACP transaction is claimed until `proof/acp_arbitration.json` contains a real job id, participants, timestamps, a deliverable, and a `completion.verified_onchain_status` of `COMPLETED`.
